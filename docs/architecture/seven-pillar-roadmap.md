# Seven-pillar roadmap: blueprint add-ons vs what ships

The owner's blueprint proposes 14 add-ons built on open digital public goods (DPGs). This page shows, for each one, what KormoPath ships today, what is partly there (with the file), and what is on the roadmap and why it is not built yet. It is written for hackathon judges, so it says plainly what is *not* built.

Checked against the code on branch `redesign/kormopath-v2`, 2026-11-17. GitHub numbers for the projects named here are in [`docs/research/seven-pillar-github-analysis.md`](../research/seven-pillar-github-analysis.md).

**Status key**
- **Shipped:** working in the app now, with no partner needed.
- **Partial:** an on-device or deterministic version ships; the DPG integration does not.
- **Roadmap:** not built. The reason is one of these: **DPI** (needs government digital public infrastructure), **Partner** (needs a licensed or operating partner), **Data** (needs a dataset we cannot honestly make up), **Regulation** (needs a licence or approval).

Rule for every row: KormoPath does not claim an integration it does not have. Where a DPG is listed as roadmap, the app uses no code from it, makes no API calls to it, and implies no endorsement by it.

**Summary:** none of the 14 add-ons is a full DPG integration today.
- **Partial (10):** 1B, 2A, 3A, 4A, 4B, 5B, 6A, 6B, 7A and 7B. An on-device, deterministic version with sources ships without a partner.
- **Roadmap (4):** 1A, 2B, 3B and 5A. Each needs government DPI, a licensed partner, validated data or regulatory approval. 7A and 7B moved to partial with Rokkha.

This is intentional. Each DPG above needs an operator, and KormoPath's job is to be the honest front door until one exists.

## What could be built next without a partner

These keep the no-accounts, no-database and deterministic rules:

1. **Rokkha red-flag scam checker** (7B): pure rules in a domain module with no imports (OTP or PIN requests, urgency, links that do not match a known bKash or Nagad domain), with unit tests. Precision and recall are measured on `/trust` against a labelled set, marked synthetic if it is synthetic.
2. **CAP alert reader** (7A): parse an official CAP XML feed if one is confirmed. Always show the issuer, the `sent` and `expires` times and a link to the source. Never generate an alert.
3. **Spray and irrigation windows** (6A): rules over the Open-Meteo forecast. Tell the farmer when, never how much.
4. **Signed badge** (2A): add a Data Integrity proof to the `lib/badge.ts` output using the server's passport key, published at a well-known URL. Keep the statement "does not prove identity".
5. **Eligibility explainer** (4A): for a few programmes, encode the official criteria with source URLs and check dates. Show "possibly eligible, confirm at the office", never "eligible".

Each new app namespace must be added to the allowlist in `lib/backup.ts`, or its data is left out of backups.

## EU AI Act and evaluation notes

In the blueprint, the AI Act applies to every pillar rather than being one add-on; 1B and 7B name specific articles.

KormoPath serves Bangladesh, so the EU AI Act (Regulation (EU) 2024/1689) applies directly only if the app is offered to people in the EU. It is still a useful checklist, and judges often ask about it. This is a reading of the Act for design purposes, not legal advice. Check the Act's current application dates before relying on them.

| Topic | Where KormoPath stands | What already supports it |
|---|---|---|
| **Transparency (Art. 50):** people must know they are talking to an AI, and AI-generated content should be identifiable | Buddy, Probaho and Outreach answers are model-generated | Every model-backed response carries `engine` (model name or `"template"`) and a visible trace from `Tracer` (`lib/trace.ts`); fallbacks show in the trace, never silently |
| **High-risk areas (Annex III): education** (evaluating learning outcomes) **and employment** (evaluating candidates) | The Examiner scores a viva and issues a Skill Passport that a client might use when hiring. This is the closest feature to Annex III | The score is computed by code, not the model; viva credit only for points the model can quote from the answer; skills rejected unless quoted from the CV; passport states it does not certify identity or skill. If offered in the EU, this feature needs a proper Annex III assessment |
| **Health** | MediScan explains text and does not diagnose or prescribe. Software with a medical purpose can fall under medical-device rules, which is the reason for the "never diagnose" rule | Emergency strip always visible; "not in our list" never means "safe"; OCR needs consent and is not cached |
| **Finance** | FeeGuard and Shohoj compute fees and budgets, and nothing scores creditworthiness (credit scoring is an Annex III use) | All money maths in `lib/finops.ts` and `lib/budget.ts`, deterministic and unit-tested; the model never computes numbers |
| **Accuracy, robustness, testing (Art. 15 spirit)** | Measured, not claimed | `/trust` publishes `lib/eval-results.json` (generated 2026-11-17): Auditor 21/21 skills backed by a quote from the CV; prompt-injection and no-skill probes passed; Outreach 0 of 6 amounts outside the contract; coach 8/8 quotes found; fees 2,000 cases (8,000 routes), 0 failures, max error 0.01 BDT; latency p50/p95 per route |
| **Record keeping and human oversight (Art. 12 / Art. 14, named in 1B)** | Partly there: every model-backed route returns a step-by-step trace, and people confirm anything parsed from speech, SMS or OCR before it is saved | `Tracer` (`lib/trace.ts`) logs model calls, tool calls, checks and fallbacks, and the UI shows them. The traces are not stored on a server (no database), so automatic long-term logging would need a privacy-reviewed log store |
| **Guardrails inside the model loop** | Violations trigger a repair retry instead of reaching the user | Zod schemas with `superRefine` (`lib/llm.ts` `structured()`): unknown $ amounts in pitches (`unknownAmounts`, `lib/grounding.ts`), invented quotes in Probaho; `null` always leads to a rule-based or template fallback |
| **Data minimisation and privacy** | No accounts, no database, data stays on the device | `lib/clientStore.ts` namespaces; `/settings` export and delete per app; `store: false` on Gemini calls; 256 KB body limit and upload allowlist in `middleware.ts` |

**Evaluation gaps to close next (honest list)**
- The eval sample sizes are small (3 CVs, 3 pitches, 3 coach runs). Fine for a hackathon; not enough for statistical claims.
- No eval yet for Buddy chat, MediScan OCR or the Crop Doctor verdicts.
- Rokkha's scam rules need a precision and recall eval before launch. A false "safe" is the costly error, so the UI should never say "safe", only "no red flags found".
- No Bangla-language eval set is published yet. The current probes are mostly in English.
